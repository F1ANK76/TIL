# 참조 타입 (string, object 등)
- **정의:** 참조 타입(Reference Type)이며 매니지드 힙(Managed Heap) 메모리에 할당되고, 한 번 생성되면 값을 변경할 수 없는 불변(Immutable)의 특징을 가집니다.
- 문제: 문자열을 수정하거나 합산할 때마다 매번 새로운 문자열 객체가 힙에 생성되므로 이전 데이터들이 가비지로 쌓여 잦은 GC 렉을 유발합니다.
- 해결: 유니티 기준, 내부에 가변 배열 구조를 가진 `StringBuilder`를 활용하여 버퍼를 통해 문자열 연산 시 발생하는 가비지 생성을 방지합니다.
- 추가 정보: `StringBuilder` 자체를 매번 `new`로 생성하면 이 또한 가비지가 되므로, 클래스 멤버 변수로 캐싱하여 `Clear()`로 내부 버퍼만 초기화해 재사용해야 완벽한 최적화(Zero-Alloc)가 가능합니다.

# 값 타입 (int, bool 등)
- **정의:** 변수가 주소값을 가지지 않고, **스택(Stack) 메모리**에 데이터 값을 직접 저장하는 타입입니다.
- 스택 오버플로우 : 함수가 끝없이 자기 자신을 호출하는 **무한 재귀 함수(Infinite Recursion)** 상황에서 스택 프레임이 계속 쌓이다가 공간이 고갈되어 발생합니다.

# C#에서 class와 struct의 차이점은 무엇인가요?
- "class는 참조 타입이고 struct는 값 타입입니다. 값 타입은 대입할 때 값 자체가 복사되고, 참조 타입은 객체에 대한 참조가 복사됩니다. 일반적으로 작은 데이터를 값 타입으로 표현하고, 상태와 동작을 가진 객체는 class로 표현합니다. Unity의 Vector3는 대표적인 struct입니다."

# OOP
- **정의:** 프로그램을 '객체'라는 독립된 단위들로 쪼개고, 이 객체들의 상호작용으로 구현하는 개발 패러다임입니다.
- 캡슐화: 변수를 변형하는 로직과 데이터를 하나로 묶고, 외부 접근을 제한(`private`)하여 데이터 오염을 방지합니다.
    - 예시: 플레이어의 `meso` 변수를 외부에서 직접 수정하지 못하게 `private`으로 막고, `GainMeso()` 메서드로만 접근하게 구현함.
- 상속: 부모 클래스의 기능을 자식 클래스가 물려받아 코드 중복을 제거하고 재사용합니다.
    - 예시: 부모 `Item` 클래스를 상속받아 `Equipment`, `UseItem` 자식 클래스를 만듦.
- 다형성: 하나의 메서드나 클래스가 상황(오브젝트 타입)에 따라 여러 가지 형태(기능)로 동작하는 성질입니다. (`Virtual`, `Override` 활용)
    - 예시: 모든 직업의 부모 클래스에 `virtual void Attack()`을 만들고, 전사는 찌르기, 마법사는 매직클로로 `override`하여 구현함.
- 추상화: 복잡한 내부 구현은 숨기고, 인터페이스나 추상 클래스를 통해 핵심적인 규칙(껍데기)만 정의하는 것입니다.
    - 예시: NPC, 포탈, 룬처럼 유저가 클릭할 수 있는 오브젝트들에 `IInteractable` 인터페이스를 장착하고 `Interact()` 메서드만 정의함.

# SOLID 원칙
- **정의:** 객체지향 프로그래밍(OOP)에서 코드를 유지보수하기 쉽고, 확장성이 뛰어나며, 버그가 잘 안 터지는 안전한 구조로 관리하기 위한 5대 설계 원칙입니다.
- S (단일 책임 원칙 - SRP): 하나의 클래스는 단 하나의 책임(역할)만 가져야 함.
    - 예시: `Player` 클래스 하나에 이동, 인벤토리, 사운드를 다 넣지 않고 `PlayerMove`, `InventorySystem`, `SoundManager`로 스크립트를 각각 쪼개어 관리함.
- O (개방-폐쇄 원칙 - OCP): 기존 코드를 수정하지 않고도 기능을 확장할 수 있어야 함.
    - 예시: 새로운 직업이 추가될 때마다 메인 코드를 열어 추가하는 게 아니라, 공통 `Job` 클래스를 상속받는 새로운 직업 클래스가 바로 추가될 수 있도록 설계함.
- L (리스코프 치환 원칙 - LSP): 자식 클래스는 언제나 부모 클래스를 완벽히 대체(치환)할 수 있어야 함.
    - 예시: 모든 몬스터의 기본인 `Monster` 클래스를 만들고, 움직이는 몬스터는 이를 상속받은 `MoveableMonster` 클래스를 거쳐 `Move()`를 구현하고 고정형 몬스터는 `Move()`가 없는 `StaticMonster` 클래스를 상속받아 구현함.
- I (인터페이스 분리 원칙 - ISP): 사용하지 않는 메서드가 포함된 거대한 인터페이스를 강제로 구현하면 안 됨.
    - 예시: `ICharacter` 하나에 모든 기능을 다 넣지 않고, `IAttackable`, `IFlyable` 같은 작은 단위로 쪼개어 각 직업에 필요한 인터페이스만 장착해서 구현함.
- D (의존역전 원칙 - DIP): 구체적인 구현 클래스에 의존하지 말고, 상위 개념인 인터페이스(추상화)에 의존해야 함.
    - 예시: 인벤토리 UI가 특정 장비 클래스를 직접 참조하지 않고, 둘 사이에 `IInventory` 인터페이스를 두고 통신하게 구현하여 시스템 구조가 바뀌어도 UI는 고장 나지 않고 독립성을 유지함.
