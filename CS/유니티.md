# 오브젝트 풀링
- 정의: 잦은 객체 생성(Instantiate)과 파괴(Destroy)로 인한 GC 발생 및 CPU 과부하를 최소화하기 위해, 객체를 풀(Pool)에 미리 만들어 두고 재사용하는 기술
- 핵심 원리: Destroy 대신 SetActive(false)로 꺼서 반납하고, 필요할 때 SetActive(true)로 켜서 대여

# 오브젝트 풀링의 한계점 및 해결책
- **문제점:** 게임 시작 시점에 풀링할 오브젝트가 너무 많으면, 초반 **메모리 점유율이 폭발적으로 상승**하고 **초기 로딩 시간**이 길어짐
- **해결책:** 유니티 내장 `UnityEngine.Pool` API를 활용하여, 초기에는 최소 수량만 생성한 뒤 풀이 모자랄 때만 유동적으로 확장하고, 최대 크기를 초과하여 반납되는 객체는 자동으로 `Destroy`

# 유니티 생명주기 (Lifecycle)
- **정의**: 유니티가 컴포넌트의 생성부터 파괴까지, 정해진 순서로 자동 호출하는 함수들

- **호출 순서**
    `Awake` → `OnEnable` → `Start` → `FixedUpdate` → `Update` → `LateUpdate` → `OnDisable` → `OnDestroy`

- **각 함수의 역할**
    - `Awake`: 생성 시 **1회**. 비활성 상태여도 호출됨 → **자기 자신 초기화**
    - `OnEnable`: 활성화될 **때마다** → **이벤트 구독**
    - `Start`: 첫 `Update` 직전 **1회**. 모든 객체의 `Awake`가 끝난 뒤 → **다른 객체 참조**에 안전
    - `FixedUpdate`: **고정 간격**(기본 0.02초) → **물리 연산**에 사용
    - `Update`: **매 프레임**(간격 가변) → 입력, 일반 로직에 사용
    - `LateUpdate`: 모든 `Update` 이후 → **카메라 추적**에 사용
    - `OnDisable`: 비활성화될 **때마다** → **이벤트 구독 해제**
    - `OnDestroy`: 파괴 시 **1회** → 최종 정리

- **핵심 1 — `Awake` vs `Start`**
    - `Awake`는 자신 초기화, `Start`는 다른 곳을 참조할 때 사용
    - `Awake` 시점엔 다른 객체가 아직 초기화 전일 수 있어 순서를 보장 못 함

- **핵심 2 — 구독은 `OnEnable`/`OnDisable` 짝으로**
    - `Awake`는 1회지만 `OnEnable`/`OnDisable`은 켜고 끌 때마다 호출 → 짝을 맞춰야 중복 구독·누수가 없음

- **핵심 3 — `Update` vs `FixedUpdate`**
    - `Update`는 프레임률에 따라 간격이 달라짐 → 이동에 `Time.deltaTime`을 곱해 프레임률과 무관하게 초당 이동량이 같도록 함
    - `FixedUpdate`는 간격이 일정 → 물리는 계산 횟수가 결과를 바꾸므로 고정 간격이 필요

# 코루틴 (Coroutine)

- **정의**: 실행을 중간에 멈췄다가, 원하는 시점에 그 자리에서 이어서 실행하는 함수
- **원리**: `IEnumerator` 반환 + `yield return`으로 중단점 표시 → 유니티가 매 프레임 다음 `yield`까지만 진행시킴
- **시작/종료**: `StartCoroutine()`으로 실행, `StopCoroutine()`으로 중단. MonoBehaviour에 종속

- **주요 대기 방식**
    - `yield return null` — 한 프레임 주도권 양도
    - `yield return new WaitForSeconds(t)` — t초 주도권 양도
    - `yield return new WaitUntil(() => 조건)` — 조건이 참이 될 때까지 주도권 양도
    - `yield return 다른코루틴()` — 그 코루틴이 끝날 때까지 주도권 양도

- **핵심 — 멀티스레드가 아니다**
    - 메인 스레드에서 실행됨. 무거운 연산을 넣으면 프레임은 그대로 멈춤
    - 프레임을 안 끊으려면 작업을 잘게 쪼개 `yield`로 나눠야 함

- **활용 사례**: 애니메이션의 타격 타이밍에 맞춰 데미지 적용, 공격 예고 후 발동, 페이드 인/아웃 같은 연출

# 드로우 콜 (Draw Call) / 배칭

- **드로우 콜**: CPU가 GPU에게 보내는 그리기 명령 1회
- **문제**: 명령을 보낼 때마다 CPU가 머티리얼·텍스처·셰이더 상태를 세팅해서 전달해야 함
    - 병목은 **그리는 양이 아니라 명령 횟수**

- **배칭**: 여러 오브젝트를 묶어 드로우 콜 하나로 그리는 것
    - **조건: 같은 머티리얼을 써야 함**
    - **Static Batching** — 메시가 달라도 되고 지형, 건물, 바위, 나무처럼 움직이지 않는 레벨 구조물
    - **GPU Instancing** — 같은 메시를 수백~수천 개 깔 때 사용
      
- **콜 "하나당 비용"을 줄이는 방법**
    - SRP Batcher (URP/HDRP) — 이름과 달리 드로우 콜을 합치지 않고 같은 셰이더면 머티리얼이 달라도 상태 전환을 생략해 **SetPass Call을 줄임**

# AI 몬스터 구현 과정

**1. 몬스터 생성**
- Monster Prefab 구성

**2. 플레이어 감지**
- 플레이어를 AI의 Target으로 설정
- Target과의 거리 및 위치를 확인하여 행동 판단에 활용

**3. AI 의사결정**
- 몬스터의 행동이 단순하고 상태 간 전환이 명확하면 State Machine 사용
- 행동과 조건이 복잡해질 경우 Behavior Tree를 활용하여 조건과 행동의 우선순위를 계층적으로 관리

**4. 플레이어 추적**
- Chase 상태에서 Target의 위치를 확인
- 단순한 환경에서는 Target 방향으로 직접 이동
- 장애물을 우회하여 이동해야 하는 경우 Pathfinding 또는 NavMesh 기반 경로 탐색 적용

**5. 공격**
- Target과의 거리가 공격 범위에 진입했는지 확인
- 공격 범위에 진입하면 공격 수행

**6. 상태 전환**
- 플레이어와의 거리, 몬스터의 체력 등의 조건을 확인하여 상태 전환
- 예: `Idle → Chase → Attack → Dead`

**7. 사망 및 정리**
- HP가 0이 되면 Dead 상태로 전환
- 사망 처리 후 몬스터를 제거하거나 Object Pool에 반환
