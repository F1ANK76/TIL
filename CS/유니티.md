# 오브젝트 풀링
- 정의: 잦은 객체 생성(Instantiate)과 파괴(Destroy)로 인한 GC 발생 및 CPU 과부하를 최소화하기 위해, 객체를 풀(Pool)에 미리 만들어 두고 재사용하는 기술
- 핵심 원리: Destroy 대신 SetActive(false)로 꺼서 반납하고, 필요할 때 SetActive(true)로 켜서 대여

# 오브젝트 풀링의 메모리 사용 과정
- **1. 공간 확보 (초기 할당):** 게임 로딩 시점에 `Queue`나 `List` 같은 자료구조를 생성하고, 설정한 풀링 길이(갯수)만큼 `Instantiate()`를 실행하여 힙(Heap) 메모리에 **연속된 오브젝트 공간을 미리 확보**합니다.
- **2. 비활성화 상태 유지:** 확보된 메모리 공간의 오브젝트들은 `SetActive(false)` 상태로 힙 메모리에 상주하며 대기합니다.
- **3. 제자리 재사용:** 오브젝트가 필요할 때 메모리를 새로 파지 않고, 이미 확보된 공간에서 주소값을 참조해 `SetActive(true)`로 켜서 사용한 뒤, 다 쓰면 다시 `SetActive(false)`로 꺼서 **그 공간 그대로 반납**합니다.
- **4. 효과:** 게임 플레이 도중 추가적인 힙 할당(`new`)과 해제(`Destroy`)가 단 1회도 일어나지 않으므로, **확보된 메모리 공간의 크기가 일정하게 유지**되며 가비지(GC)가 전혀 발생하지 않습니다.

# 오브젝트 풀링의 한계점 및 해결책
- **문제점:** 게임 시작 시점에 풀링할 오브젝트가 너무 많으면, 초반 **메모리 점유율이 폭발적으로 상승**하고 **초기 로딩 시간**이 길어집니다.
- **해결책:** 유니티 내장 `UnityEngine.Pool` API를 활용하여, 초기에는 최소 수량만 생성한 뒤 풀이 모자랄 때만 유동적으로 확장하고, 최대 크기를 초과하여 반납되는 객체는 자동으로 `Destroy`

# 오브젝트 풀링 자료구조별 장단점

### 1. Queue (큐)
- **장점:** 선입선출(`FIFO`) 구조로 작동하여 대여(`Enqueue`)와 반납(`Dequeue`) 속도가 `O(1)`로 가장 빠르고 안정적임. 순서대로 돌려쓰기 때문에 모든 객체가 골고루 재사용
- **단점:** 중간에 끼어있는 특정 오브젝트를 꺼내거나 삭제하는 중간 제어가 불가능

### 2. Stack (스택) - 유니티 내장 풀 아키텍처
- **장점:** 후입선출(`LIFO`) 구조로, 대여(`Pop`)와 반납(`Push`) 속도가 `O(1)`로 큐만큼 빠름. 방금 반납된 객체를 다시 쓰기 때문에 CPU 캐시 효율 측면에서 미세하게 유리할 수 있음
- **단점:** 큐와 마찬가지로 중간 데이터 제어가 불가능하며, 풀이 넉넉할 경우 뒤쪽에 있는 객체들은 평생 사용되지 않고 메모리만 차지할 수 있음

### 3. List (리스트)
- **장점:** 인덱스 접근이 가능하여 중간에 있는 오브젝트가 먼저 파괴되거나 활성화 상태를 임의로 변경해야 할 때 **중간 데이터 제어**가 매우 유용
- **단점:** 대여할 대상을 찾기 위해 리스트를 처음부터 끝까지 훑어야 하므로(`Loop`), 풀의 크기가 커질수록 탐색 속도(`O(N)`)가 느려져 인게임 렉을 유발할 수 있음

### 4. Array (배열)
- **장점:** 크기가 고정되어 있어 메모리 할당이 매우 안정적이며, 고정된 인덱스로 접근하므로 탐색 속도가 빠름
- **단점:** 크기가 고정(`Fixed Size`)되어 있어, **유동적 확장(Dynamic Growth)이 원천적으로 불가능**
