# OOP
- **정의:** 프로그램을 '객체'라는 독립된 단위들로 쪼개고, 이 객체들의 상호작용으로 구현하는 개발 패러다임
- **캡슐화:** 데이터와 그 데이터를 다루는 로직을 하나로 묶고, 외부 접근을 제한해 데이터 오염을 방지
    - 예시: 몬스터의 체력을 외부에서 직접 다루지 못하게 하고, `TakeDamage`로만 바뀌도록 구현
    - 이유: 체력바 갱신·사망 이벤트 발행 같은 처리를 외부에서 각자 하면 중복되고 누락될 수 있음

- **추상화:** 복잡한 구현은 감추고, 무엇을 하는지 본질만 남겨 정의하는 것
    - 예시: 물약과 장비는 하는 일이 완전히 다르지만, 공통점은 "위치를 받아 아이템을 떨군다"뿐이라 DropSource 부모에는 그 한 줄만 정의
    - 이유: 공통 부분을 최소로 잡아야 새로운 드롭 종류가 그 틀에 맞출 수 있기 때문
      
- **상속:** 공통된 데이터와 기능을 부모에 두고, 자식이 물려받아 재사용하는 것
    - 예시: 물약 드롭과 장비 드롭의 공통 부분을 DropSource 부모에 두고, 자식은 무엇이 떨어질지만 정의
    - 이유: 드롭 종류를 추가할 때 생성·이동 같은 중복 코드를 다시 구현하지 않아도 됨
      
- **다형성:** 같은 호출이 실제 객체가 무엇이냐에 따라 다르게 동작하는 것
    - 예시: 드롭 종류를 확률로 뽑은 후 같은 함수를 호출해도, abstract로 뽑힌 종류에 맞는 아이템이 드롭되도록 구현
    - 이유: 드롭 종류를 추가해도 뽑아서 호출하는 코드는 수정 불필요

# SOLID 원칙
- **정의:** 객체지향 설계에서 유지보수와 확장이 쉬운 구조를 만들기 위한 5가지 원칙
- S (단일 책임 원칙 - SRP): 클래스는 하나의 책임만 가진다
    - 적용: GameManager를 만들지 않고 스테이지, 전투, 패링 매니저 등으로 분리
- O (개방-폐쇄 원칙 - OCP): 확장에는 열려 있고, 수정에는 닫혀 있다
    - 적용: 드롭 종류를 추가해도 DropCoordinator는 수정하지 않고, 리스트에 컴포넌트만 추가
- L (리스코프 치환 원칙 - LSP): 자식은 부모 자리에 넣어도 문제없이 동작해야 한다
- I (인터페이스 분리 원칙 - ISP): 안 쓰는 기능까지 강제하지 말고 잘게 나눈다
- D (의존역전 원칙 - DIP): 구체 클래스가 아니라 추상에 의존한다
 
# 디자인 패턴
- **정의:** 소프트웨어에서 반복적으로 발생하는 설계 문제를 해결하기 위한 검증된 설계 방법
- Singleton : 객체를 하나만 만들고 어디서든 접근
  - 예시 : 게임 매니저 등 전역적으로 하나만 필요한 객체
- Observer : 한 객체의 상태 변화가 다른 객체들에게 알려짐
  - 예시 : 이벤트, UI 갱신, 몬스터 사망 알림
- Object Pool : 객체를 미리 생성해 재사용
  - 예시 : 총알, 이펙트, 몬스터처럼 생성/삭제가 많은 객체
